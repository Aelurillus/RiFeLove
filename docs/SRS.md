# RifeLove software requirements specification

Version 0.2 status reconciliation, 2026-10-31. The authoritative product scope is [the original Master Plan V1.0](MASTER_PLAN_V1.0.zh-CN.md), extended by the user's restoration requirements and the explicit [non-Qt, desktop-only scope amendment](MASTER_PLAN.md). The current client is the Windows Win32/Direct2D/DirectWrite desktop. Qt/QML is legacy source; the CLI is internal developer/test tooling, not a product executable or package prerequisite. The original desktop capabilities and all applicable P0, P1 and P2 requirements remain required: a pending item has not been removed from the final product.

Runtime processing is offline. Source videos, inference, imported model packs, settings, task databases/history, logs, caches and checkpoints stay local. Model discovery/import and SHA-256/sidecar checks use local files; missing packs fail with an actionable local path rather than triggering a download. No platform account, model catalog, telemetry, update service or cloud connection is required for processing. Alibaba Cloud OSS is disabled. The previously authorized Storj major-release backup is also disabled until separately configured and verified; it is not part of the runtime path. Any future backup may contain only reviewed release artifacts, never user media, models with unresolved redistribution rights, credentials or task data. Source-repository publication is a separate authorized developer action.

`Partial` means there is bounded implementation/test evidence but the full requirement is still open. `Pending` means the product workflow or its acceptance evidence is missing. Several records below describe legacy Qt workflows or core-level tests; neither establishes native UI parity. Source code or tests that have merely been added are not recorded as passing evidence. The dynamic-exposure evidence explicitly listed below was executed in the local Release build; it is not a whole-product acceptance result.

## Dynamic exposure and platform-copy evidence

The executed Release checks are `MotionBlurSampling.*`, `MotionBlurExposure.*` and `MotionBlurPipeline.*`. The five production-path tests are registered in `tests/unit/motion_blur_test.cpp` and implemented in `tests/integration/motion_blur_pipeline_test.hpp`. They call the actual pipeline with lossless tagged SDR clips and a deterministic linear backend using real CUDA buffers. The matrix covers ten source/target combinations, with 12 output frames per combination; successful exposure plus explicit fallback equals newly processed output, and normal continuous motion has zero fallback. The cut test rejects cross-scene exposure, the very short clip drains EOF edge holds, and budget/cancellation tests verify no published output or leaked partial file. Local evidence: `build/windows-release/motion-blur-regression.xml` (ignored build artifact), 17 passed, zero failed/skipped, 2026-10-31.

Limits are explicit: these small numerical fixtures do not qualify RIFE/TensorRT image quality, 1080p/4K or long-video performance, the full native UI/package, HDR exposure, or any platform upload/playback tier. Matroska source timestamps are quantized to milliseconds; the pipeline consumes those actual rational PTS. Planner tests additionally cover nonzero-origin VFR, 180/360-degree shutters, 4/16 samples and cuts/abnormal/duplicate barriers between sample times. Prepared source-window floats are bounded by `hostFloatBufferLimit` (default 512 MiB) and 4096 frames; this is not a total-process RAM cap. An insufficient full shutter fails explicitly. Reports distinguish integrated frames, fallback frames/reasons, edge holds and peak window use, counting this execution rather than reused checkpoint output. Enabled checkpoints bind motion-blur algorithm version 2 and cannot mix old four-frame results. See [platform export contracts](architecture/PLATFORM_EXPORT.md) for presets and platform-source distinctions; accepting a high-rate file is not evidence of high-rate playback or a verified "240 FPS-like" viewing result.

## Final completion gate

In addition to R28, the user requires motion-aware temporal restoration for compression artifacts, lost detail and noise, alongside optional natural motion blur. The three restoration controls also need independent content-adaptive estimates and user adjustments relative to automatic settings, reflecting the interaction described in [Topaz's public documentation](https://docs.topazlabs.com/topaz-video/filters/enhancement). This is a behavioral reference, not a claim of using or reproducing proprietary models. A qualified implementation must demonstrate temporal stability and cut/edge behavior on video, preserve the media timeline, and document model provenance, licensing, quality and GTX 1660 SUPER performance. Existing single-frame x2 super-resolution and deblur evidence does not establish that capability.

All seven Master Plan delivery groups remain unaccepted: complete desktop application, real RIFE GPU interpolation, complete media/color, queue/recovery/models, preview/quality/quality restoration/encoding, tests/benchmarks/docs, and installable compliant continuously maintainable distribution. Passing the current foundation suite proves only the behaviors explicitly covered above. The goal remains active until every required capability and release gate has direct evidence.
