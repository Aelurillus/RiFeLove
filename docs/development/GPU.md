# Native CUDA and ONNX Runtime development

The application now keeps one reviewed native runtime set and root ONNX environment per process while releasing individual sessions/buffers per task. Runtime directory changes require application restart. This lifecycle policy was added after an intermittent cuDNN access violation during repeated task sessions; the [queue regression](QUEUE.md) executes 20 sessions and compares decoded pixels/timing. It does not establish broad hardware or multi-hour stability. Upstream ONNX Runtime also manages provider initialization/shutdown at environment/library scope ([pinned v1.22 source](https://github.com/microsoft/onnxruntime/blob/v1.22.0/onnxruntime/core/session/provider_bridge_ort.cc)); that source is context for the lifecycle design, not proof of the local crash's root cause.

The application runtime remains native C++20. Python/PyTorch are used only for source review, export and reference generation.

## Driver primitives and evidence

`src/gpu/cuda_device.*` loads `nvcuda.dll` from Windows System32, retains a primary context, creates a nonblocking stream and owns allocations through reference-counted buffers. Allocation requests are bounded by a tracked budget. The default buffer budget is the smaller of one quarter of currently free memory and 1 GiB. The RIFE video path now keeps a two-slot input buffer pool: it reuses an exact-size allocation only after all inference aliases have been released, and evicts idle entries before retrying after an allocation-budget failure. Active buffers are not reused. This does not bound other libraries' allocations or all VRAM usage.

Local hardware: GTX 1660 SUPER, compute 7.5, driver 560.94, driver CUDA API maximum 12.6, 6 GiB VRAM. Four hardware tests passed in Debug and Release: actual device/memory query, budget release/reallocation, host/device and device/device transfer equality with range/cancel errors, and buffer lifetime after the device wrapper closes. The new Release pool test also passed: it confirms exact-size reuse only after references are released, eviction of idle buffers when the cache is full, and budget recovery. A separate test rejects negative device indices before driver loading. Driver API support is not an installed Toolkit version or a codec capability claim.

FFmpeg CUDA/NVDEC decode is now available to native video jobs and `media-scan --decode cuda`. On this workstation, a synthetic 320x180 H.264 clip decoded through CUDA, and CPU versus NVDEC YUV output had the same SHA-256 (`230FECC613D8E6855501D95FFC24B69F657F64C50F8E5BC61B4344FC85F0DBA4`, 1,296,000 bytes). End-to-end pipeline integration verifies source-frame preservation and a BT.601-family VUI/container conflict after NV12 host transfer. The decoder summary records the actual decoder and acceleration path; decoder/device/format negotiation failures fall back to software before frames are delivered. A failure during a later hardware-frame transfer fails the job instead of replaying callbacks, and broader GPU/driver, resolution and long-video qualification remains open.

## Native backend boundary

`IInterpolationBackend` exposes asynchronous futures over owned normalized RGB FP32 NCHW device frames. `OnnxCudaBackend` serializes work on a worker thread with a bounded queue, uses the owned CUDA stream and ONNX I/O binding, and accepts exclusive reusable outputs. Endpoints use exact device copies. Request cancellation uses stop tokens and ONNX termination; error/cancel paths synchronize the stream before releasing storage. Replacement and profiling require an idle backend. Device-buffer aliases must remain immutable until their future completes.

ONNX Runtime uses its public C function table; no MSVC C++ object crosses into the MinGW application. Model bytes are size-bounded and SHA-256 verified before `CreateSessionFromArray`; external-data packs are not supported by this adapter. Paths must stay within the pack, including resolved links. Descriptor hashes are integrity checks, not signatures or proof of an author's identity. Trusted catalogs/custom-model policy and sandboxing still belong to the future model manager.

The native backend passes six small-profile SDR8 numerical comparisons and 36 endpoint, pre-cancel, invalid-input and exclusive-output checks on the local GPU. Debug and Release each pass 32 CTest checks including the native validator. Five further consecutive Release native runs passed. Maximum error is `0.001534104347229004`; minimum PSNR is `83.86017808054655` dB. Profiling records 336 CUDA Conv, 42 ConvTranspose and 108 GridSample calls across six cases. CPU shape/scalar tensors have at most four elements; image-sized CPU fallback is rejected by validation.

Native dependencies, including cuDNN's split modules, are preloaded explicitly from the SDK directory with DLL-directory and System32 search flags; system PATH is unchanged. An initial cuDNN child-module load failure was fixed before numerical acceptance. Heuristic convolution selection subsequently exceeded the fixed numerical gate in one Release run; the runtime now uses the documented `DEFAULT` implicit-precomputed-GEMM baseline with TF32 disabled. Faster algorithms require separate qualification. No tolerance was relaxed for this native failure. These tests establish small-profile numerical behavior, not video quality, full shape coverage, in-flight cancel/queue reliability or final performance acceptance.

## Pinned local setup

`tools/development/onnx-cuda-sdk.lock.json` pins ONNX Runtime GPU 1.22.0, its C header, nlohmann JSON 3.12.0, CUDA runtime 12.8.90, cuBLAS 12.8.4.1, cuFFT 11.3.3.83 and cuDNN 9.8.0.87. The provider's PE imports were inspected to identify the required DLLs; cuFFT is a binary dependency even though RIFE itself does not request FFT operations. NVIDIA wheels supply native DLLs only; the application does not import Python. The setup helper uses cached assets by default and requires `-AllowDownload` for acquisition. It does not change system PATH, the driver or installed system runtimes.

```powershell
.\tools\development\setup-onnx-cuda.ps1 -AllowDownload -DependencyRoot C:/itzming/dependences
cmake --preset windows-dev -DRIFELOVE_BUILD_ONNX_CUDA=ON -DRIFELOVE_ONNX_ROOT=C:/itzming/dependences/onnxruntime-win-x64-gpu-1.22.0 -DRIFELOVE_JSON_ROOT=C:/itzming/dependences/nlohmann-json-3.12.0
cmake --build --preset windows-dev
.\build\windows-dev\rifelove-validate-cuda.exe models/cache/rife-4.25-fp32-sdr8-v2 C:/itzming/dependences/onnxruntime-win-x64-gpu-1.22.0/lib build/windows-dev/native-cuda-validation.json
```

Set `RIFELOVE_TEST_RIFE_PACK` to the qualified local pack directory to include `OnnxCuda.NativeReference` in CTest; it is enabled in the current local build caches. The validator verifies reference hashes, compares multiple shapes/timesteps, tests exact endpoints, pre-cancellation, invalid inputs and output reuse, and parses ONNX profiling. Convolution, transpose convolution and GridSample must actually execute on CUDA. CPU shape/scalar operations are bounded and reported separately. The ORT arena has its own 1 GiB default limit, which is not a total-process VRAM cap.

TensorRT needs a runtime directory containing both ONNX Runtime 1.22 and the matching TensorRT 10.9/CUDA/cuDNN DLLs. This workstation keeps the combined runtime under `C:/itzming/dependences/rifelove-tensorrt-10.9.0.34/onnxruntime-win-x64-gpu-1.22.0/lib`; the ordinary ONNX CUDA SDK directory alone does not contain `nvinfer_10.dll`. Configure `-DRIFELOVE_TENSORRT_RUNTIME_DIR=<combined runtime>` to add `OnnxTensorRt.NativeReference` to CTest. The workstation package links `runtime/` to this combined directory and runs the TensorRT FP32 numerical check for each included model before it is considered packaged.

Before the first TensorRT engine is created, the process default DLL search is restricted to the app directory, explicitly registered runtime directories, and `System32`; the selected TensorRT builder DLLs are then pinned by full path. TensorRT opens its builder resource by basename, so `AddDllDirectory` alone is insufficient unless the process default search includes user directories. This avoids relying on or modifying `PATH` and prevents an unrelated runtime from winning a same-name lookup. `Pipeline.TensorRtRuntimeIsolation` puts an older ONNX directory first on purpose, clears the local engine cache, builds a 320x180 TensorRT engine and verifies successful interpolation plus the active backend. On the current workstation the old and selected builder DLLs have different sizes (1.42 GB and 1.97 GB); the test protects this concrete version-collision case.

This workstation uses ONNX Runtime 1.22.0, CUDA Runtime 12.8, TensorRT 10.9.0.34 and a GTX 1660 SUPER (compute 7.5, 6 GiB). Native TensorRT validation passes six RIFE 4.22 Lite, 4.25, 4.25 Lite and 4.26 FP32 SDR8 reference cases at 64x64 and 128x192, within the existing `0.5/255` maximum-error and 80 dB PSNR limits. 4.22 Lite remains an optional candidate and is not the default. For the exact 4.26 model hash `e6df922305d77a7db5685a9f964bae3736cc1f394cd914f34db4c1411e5c0726`, FP32 maximum error is 0.00183 and minimum PSNR is 85.94 dB. RIFE 4.25 Lite reaches maximum TensorRT FP32 error 0.00038244 and minimum PSNR 93.96 dB. Profiling confirms execution by the fused `TensorrtExecutionProvider` kernel; all 36 endpoint/cancellation/input/output-buffer checks pass. A dynamic min64/opt720p/max4K profile built a local engine; some 4K tactics requested more than the GPU's 6 GiB and were skipped. A synthetic 720p comparison of 60 source frames and 60 inserted frames measured non-source-frame PSNR/SSIM of 30.27 dB/0.9643 for 4.22 Lite, 30.61 dB/0.9649 for 4.25, 30.88 dB/0.9681 for 4.25 Lite, and 30.62 dB/0.9647 for 4.26. This short synthetic sequence is only a regression signal, not a visual quality ranking. A tagged synthetic 720p BT.709 clip also completed the full RIFE/TensorRT path at 30 to 60 FPS: 15 source frames became 30 output frames, 24 generated by RIFE, the original FLAC audio remained, and duration stayed 0.5 s. A separate synthetic 96x64 BT.709 10-bit RIFE job now verifies automatic fallback from NVENC's unsupported pixel format to libaom AV1, while retaining `yuv420p10le`, color tags, frame count and rational timing. These synthetic results do not qualify real-content quality, thermal behavior, other GPUs/drivers or end-to-end throughput. The engine cache is local and keyed by model, GPU, ONNX Runtime/TensorRT/CUDA versions, precision, profile and workspace.

The current FFmpeg SDK exposes NVENC but its open attempt returns `Function not implemented` on this workstation: FFmpeg reports it needs NVENC API 13.0 while the installed driver exposes 12.2, and requires driver 570.0 or newer. The media preflight now queries the NVIDIA driver API directly and turns that mismatch into the existing localized version/driver guidance. Studio's source-profile preflight selects a compatible software encoder before starting when that check fails; the 8-bit SDR example uses software H.264, while the synthetic 10-bit pipeline selects AV1. CLI `auto` attempts NVENC at job start and then falls back after either initialization or source-pixel-format rejection. The 720p end-to-end run above confirmed that software H.264 produced a valid video and retained audio; it is not evidence that NVENC hardware encoding works. To enable hardware encoding with this FFmpeg build, install an NVIDIA driver that supports API 13.0 (570.0 or newer); a future FFmpeg rebuild against API 12.2 could retain support for older drivers, but has not been qualified yet.

TensorRT mixed-FP16 tactic selection is available only in the opt-in native validator; normal Studio/queue jobs remain FP32. On the GTX 1660 SUPER, RIFE 4.26 FP16 failed all six SDR8 reference cases with maximum absolute error 0.953 and minimum PSNR 16.53 dB. The same model passed all six FP32 cases against the same reference, so this is a real precision failure, not a runtime/model mismatch. The precision-specific cache identity is retained. Do not enable FP16 for users until selective precision or another implementation passes the existing numerical gate and visual qualification. To reproduce the current result, pass the combined TensorRT runtime directory:

```powershell
.\build\windows-qt-release\rifelove-validate-cuda.exe `
  models/cache/rife-4.26-fp32-sdr8-v1 `
  C:/itzming/dependences/rifelove-tensorrt-10.9.0.34/onnxruntime-win-x64-gpu-1.22.0/lib `
  build/windows-qt-release/fp16-native-qualification-20261025/tensorrt-fp16-report.json tensorrt-fp16
```

A passing small-fixture report is necessary but not sufficient to enable FP16 in Studio or the queue. Per-model full-resolution numerical and visual quality, memory use, stability and end-to-end speed still need qualification. CUDA graphs, decode/inference/encode overlap, broader NVDEC GPU/driver qualification, tiling, broader shape/content and performance qualification also remain open. The source-frame pool's GPU allocation behavior is verified; its effect on full-pipeline throughput still needs measurement.
