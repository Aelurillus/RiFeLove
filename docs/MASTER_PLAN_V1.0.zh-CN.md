# RifeLove — 最终产品总体开发计划

RifeLove Master Plan · Version 1.0 · 2026-10-17

完整产品蓝图 · 非 MVP

**范围修订（2026-10-28）：** 用户确认最终交付只做 Windows 桌面应用，主界面不使用 Qt/QML，CLI 不属于用户交付范围，阿里云 OSS 不再使用。本文中原有的 Qt 与 CLI 描述由此修订覆盖，批量处理和自动化体验通过桌面任务队列实现。此前授权的 Storj 大版本备份继续作为待配置事项。具体实施与验收见 [原生桌面迁移计划](development/NON_QT_EXECUTION_PLAN.zh-CN.md)。

项目名称： RifeLove 产品类型： 开源离线 AI 视频补帧桌面软件 目标平台： Windows 10 / 11 x64 硬件平台： NVIDIA GPU 核心目标： 高画质、高性能、稳定性、易用性兼顾 最终交付： 完整桌面应用、可分发安装包、开源代码、模型管理体系、开发文档和自动化测试系统

RifeLove 的目标不只是将 30 FPS 视频转换为 60 FPS，而是成为一款拥有专业视频处理能力、可扩展 AI 推理架构和现代桌面体验的完整软件。

本计划描述的是最终产品应该具备的全部能力，而不是第一版最小可用功能。所有模块都纳入最终架构，但仍然按依赖关系分阶段实现。

## 一、产品定位与设计原则

Quality First, Performance Always

保持细节、运动连贯性和时间准确性，同时充分发挥 NVIDIA GPU 的性能。

Non-destructive Processing

不修改原始视频，默认输出新文件，保留可保留的元数据、音轨和字幕。

Native GPU Pipeline

以 NVIDIA CUDA 为主要计算平台，优先减少不必要的显存复制和 CPU/GPU 同步。

Modular and Open

AI 模型、推理后端、视频编解码器、输出策略独立设计，方便维护和扩展。

### 模块边界

`UI` 不直接调用 CUDA 或 FFmpeg。所有视频任务通过应用服务层提交给 Core Engine。

`Interpolation Engine` 只关心输入帧、目标时间和模型输出，不负责文件格式或 UI。

`Media Engine` 负责正确处理视频流、音轨、字幕和容器格式。

`Quality Engine` 决定哪些帧可以安全插值、哪些帧需要回退或标记。

这样后续替换 RIFE 版本、增加新的推理后端或重做界面，都不需要重写整个软件。

## 五、AI 模型与推理引擎完整方案

这是 RifeLove 最重要的技术部分。

### 5.1 模型体系

RifeLove 不应该只绑定一个固定版本的 RIFE，而应该建立统一的模型接口。

| 模型档位     | 目标      | 实现策略             |
| -------- | ------- | ---------------- |
| Fast     | 最快处理速度  | 选择经过验证的轻量模型和优化配置 |
| Balanced | 默认推荐    | 兼顾速度、清晰度、运动连贯性   |
| Quality  | 尽可能减少伪影 | 使用更高质量的模型及保守回退策略 |
| Custom   | 高级用户    | 导入符合适配器规范的模型     |

这些是软件预设，不应假定某个模型在所有视频中始终优于其他模型。

模型接口设计为：

```
struct InterpolationRequest {
    GpuFrame frame0;
    GpuFrame frame1;
    float timestep;
};

class IInterpolationBackend {
public:
    virtual ~IInterpolationBackend() = default;

    virtual ModelCapabilities capabilities() const = 0;
    virtual void loadModel(const ModelConfig&) = 0;
    virtual GpuFrame interpolate(
        const InterpolationRequest& request
    ) = 0;
};
```

正式实现还需要显式支持异步执行、CUDA Stream、错误返回、取消请求和输出缓冲复用。

### 5.2 模型开发流程

1. 收集候选 RIFE 模型，确认许可证、模型权重来源和架构特征。
2. 使用 PyTorch 建立参考推理结果，记录精度和性能基线。
3. 导出 ONNX，并验证动态时间参数、输入分辨率及算子兼容性。
4. 接入 ONNX Runtime CUDA，逐帧比较与 PyTorch 的数值差异。
5. 转换为 TensorRT 引擎，测试 FP16、显存消耗和不同分辨率。
6. 建立模型注册表，记录模型版本、SHA-256、许可证、能力和适用场景。

TensorRT 引擎缓存需要考虑 GPU 架构、TensorRT 版本、模型版本和优化配置。默认不把某台开发机器生成的引擎直接当作所有用户的通用引擎。

### 5.3 模型性能优化

完整版本纳入以下优化方向：

- FP16 混合精度推理，保持必要的数值稳定性。
- CUDA Graph，减少适合固定形状工作负载的提交开销。
- GPU 缓冲池，避免重复分配显存。
- CUDA Stream，实现安全的流水线重叠。
- TensorRT Engine Cache，避免重复编译模型。
- 分辨率 Profile 管理，降低不同输入尺寸的引擎构建成本。
- 自适应显存预算，避免高分辨率视频导致 OOM。
- 可选 Tiling，针对超高分辨率输入进行重叠分块与融合。

不盲目追求最大并发，因为插帧通常依赖相邻帧，过度并行可能导致显存占用增加，甚至降低整体吞吐。

## 六、视频处理与时间轴系统

### 6.1 完整处理流水线

01

Media Probe

读取流信息、时间基、HDR 元数据、音轨与字幕

02

Decode

FFmpeg 解码、帧重排、时间戳恢复

03

Preprocessing

像素格式转换、色彩处理、GPU 上传

04

Timeline Scheduler

计算目标输出帧对应的输入帧和时间位置

05

Scene Analysis

检测切镜、异常帧、无效运动区域

06

RIFE Inference

生成中间帧、执行模型推理与质量策略

07

Postprocessing

恢复输出色彩格式、位深、必要的元数据

08

Encoding

NVENC 或适当的软件编码回退

09

Mux & Validate

封装音轨字幕、验证帧数、时长及文件完整性

### 6.2 精确帧率转换

最终必须支持：

- 整数倍转换：30 → 60、30 → 120、60 → 240。
- 非整数倍转换：24 → 60、25 → 60、30 → 144。
- 23.976、29.97、59.94 等分数帧率。
- 可变帧率 VFR 输入。
- 固定帧率 CFR 输出。
- 可选择保留源时间轴特征的高级输出模式。

使用有理数时间基与整数时间戳，避免长期累积的浮点误差。

关键原则：输出视频时长不应因为补帧而改变。 最终一帧的处理、音轨边界和容器时间基必须有专门的测试。

### 6.3 音频与字幕

默认策略是尽可能直接复制原始音轨，而不是重新编码。

需要处理多音轨、不同音频编码、字幕流、章节、语言标记、旋转信息，以及容器不支持某种流格式时的兼容性问题。

## 八、RifeLove 最终 UI / UX 规划

采用 Qt Quick / QML 构建现代深色桌面界面，视觉上保持简洁，避免把大量技术参数直接堆给普通用户。

### 主要页面

Home / Workspace

视频拖入区、最近任务、GPU 状态、快捷预设、开始处理入口。

Interpolation Studio

源视频信息、目标 FPS、模型、质量预设、输出格式、编码参数。

Comparison Viewer

原片与补帧预览、分屏比较、同步播放、逐帧分析和可疑帧定位。

Task Queue

模型安装、版本切换、模型校验、推理后端设置、引擎缓存管理。

### 软件交互规范

普通用户只需要选择视频、目标帧率、质量预设和输出位置。

高级用户可以展开专业参数，包括 TensorRT 精度、推理后端、色彩管理、显存预算、编码器参数及切镜阈值。

所有危险或可能导致画质下降的参数都需要有明确说明，且支持恢复默认值。

## 九、GPU 性能与资源管理

最终版本应支持 GPU 能力检测，并根据硬件自动选择可用功能。

| 组件     | 设计                      |
| ------ | ----------------------- |
| GPU 检测 | GPU 型号、驱动、可用显存、计算能力     |
| 推理精度   | FP16 优先，必要时使用 FP32      |
| 显存管理   | 显存池、容量预算、OOM 回退         |
| 解码     | NVDEC，必要时回退 CPU         |
| 编码     | NVENC，按 GPU 实际支持的格式选择   |
| 流水线    | 解码、推理、编码阶段异步执行          |
| 缓存     | 模型缓存、TensorRT 引擎缓存      |
| 调度     | 自动缓冲大小、受控任务并发           |
| 监控     | FPS、GPU 利用率、显存、温度（可获取时） |

性能优化要用数据驱动，重点监控端到端处理速度，而不是只展示神经网络单次推理耗时。

### 性能指标

建议建立的正式性能验收指标

# ≥ 99.9%

受控兼容性测试任务成功率目标

# 0

容忍未报告的音画时间轴错误

# 100%

异常退出后任务状态可识别

# 可复现

同硬件与配置下性能测试

这些是待验证的工程目标，不是当前实测结果。实际 FPS 性能需按 GPU、模型、分辨率和编码配置分别制定基线。

不能承诺所有 NVIDIA 显卡都能实时处理 4K/120 FPS。软件应该明确区分输出视频帧率与实际处理速度。

## 十、任务系统、持久化与异常恢复

RifeLove 最终应当能够可靠地处理数小时的视频，而不仅是几秒钟的测试片段。

### 任务状态机

最终需要支持任务暂停、继续、取消、重试和历史记录。

特别注意：暂停与断点恢复不是同一个功能。 断点恢复需要在安全的输出分段边界保存进度、时间戳和编码状态，并在恢复时正确拼接输出。不能仅靠记住上一帧序号实现。

建议 SQLite 存储任务配置、模型版本、文件校验信息、任务状态和分段记录。

## 十二、完整开发路线图

这是面向最终产品的实施路线，而不是只做 MVP 就停止。

Phase 1

工程基础与核心架构

Phase 2

完整媒体引擎

验收：真实 AI 插帧端到端运行

Phase 4

高性能 GPU 引擎

NVDEC/NVENC、显存池、异步流水线、引擎缓存、性能分析

验收：建立可复现性能基线

Phase 5

质量保护与色彩管理

切镜检测、伪影策略、HDR/SDR、10-bit、VFR、复杂素材兼容

验收：质量回归测试达标

Phase 6

完整桌面体验

QML UI、实时预览、批量任务、模型中心、预设、国际化

Phase 7

可靠性与专业功能

断点恢复、异常重试、诊断报告、高级编码和质量分析

Phase 8

正式发布与持续维护

验收：稳定版发布并进入维护周期

这些阶段存在一定并行空间。例如，UI 可以在媒体引擎开发期间同步推进，但 GPU 优化必须建立在正确的插帧结果和稳定的测试基线上。

不建议在尚未验证模型正确性之前投入大量时间进行 CUDA 微优化。

## 十三、测试、质量评估与验收

最终产品必须同时通过功能测试、性能测试、视觉质量测试和稳定性测试。

### 测试素材矩阵

| 测试维度   | 覆盖范围                         |
| ------ | ---------------------------- |
| 分辨率    | 480p、720p、1080p、1440p、4K     |
| 输入 FPS | 23.976、24、25、29.97、30、60、VFR |
| 输出 FPS | 60、120、144、240、自定义           |
| 视频类型   | 实拍、游戏录制、动画、屏幕录制              |
| 运动类型   | 慢动作、快速平移、遮挡、镜头切换             |
| 编码格式   | H.264、HEVC、AV1 及支持的其他输入      |
| 色彩     | SDR、HDR、8-bit、10-bit         |
| 视频长度   | 短片段、长视频、多小时素材                |
| 异常情况   | 文件损坏、磁盘不足、显存不足、意外退出          |

### 视觉质量评估

对于有高帧率真实参考的视频，使用 PSNR、SSIM、LPIPS 等指标评估生成帧质量，并结合运动区域分析。

对于没有真实参考的普通录制视频，主要采用人工盲测、时间一致性检查和伪影标记，避免把无参考指标当作绝对画质评分。

### 正式发布门槛

- 所有 P0 功能实现并通过验收。
- 不出现未报告的音画同步错误。
- 镜头切换、非整数帧率和 VFR 转换测试通过。
- 支持矩阵内的 GPU 和驱动组合经过实际测试。
- 长视频处理和中断恢复通过稳定性测试。
- 无已知的高严重性安全漏洞或数据丢失缺陷。
- 安装、卸载、模型下载、首次启动流程经过验证。
- 第三方许可证、模型权重和分发条件审查完成。

## 十四、开源与发布策略

建议采用 核心引擎与桌面 UI 均开源 的方式，不设计人为限制导出帧率、分辨率或处理时长的付费门槛。

项目许可证建议优先评估 Apache-2.0 或 GPL-3.0，但必须先完成 FFmpeg 构建配置、Qt 使用方式、模型代码与权重许可证的兼容性审查，不能仅凭项目开源就认定所有组件可自由再分发。

最终发布渠道以 GitHub Releases 为主，提供 Windows 安装包和便携版本。

发布内容包括：

- Windows x64 安装包与便携版。
- SHA-256 校验信息。
- 完整源代码及构建指南。
- 支持的 GPU、驱动和模型列表。
- 更新日志、已知问题、性能基准。
- 用户指南、开发者指南和故障排查文档。

更新机制应支持版本校验、下载完整性检查和失败回退。模型更新与应用更新分开管理，避免每次升级都重新下载大型模型。

## 十五、核心风险与应对

| 风险                    | 应对策略               |
| --------------------- | ------------------ |
| RIFE 模型 TensorRT 转换失败 | ONNX CUDA 作为稳定兼容后端 |
| 不同 GPU 性能差异大          | 建立 GPU 能力矩阵和分级优化策略 |
| 4K 视频显存不足             | 显存预算、分块处理和安全回退     |
| 高速运动伪影                | 场景分析、质量预设和保守回退     |
| HDR 色彩偏差              | 独立色彩管理管线和 HDR 测试   |
| VFR 音画不同步             | 以 PTS 为核心设计时间轴     |
| 软件崩溃导致任务丢失            | 持久化任务状态与分段恢复       |
| 第三方许可证限制              | 早期开展合规审查           |
| CUDA/TensorRT 版本不兼容   | 固定构建环境、版本矩阵与缓存失效机制 |

## 十六、最终完成定义

RifeLove 的最终目标不是达到某个版本号，而是具备以下完整使用体验：

用户可以将已经录制好的视频拖入 RifeLove，选择目标 FPS 和画质预设，软件自动检测 NVIDIA GPU、加载适当的 RIFE 模型、分析视频时间轴和镜头切换，通过 GPU 加速完成补帧，并输出音画同步、色彩正确、可正常播放的视频。

高级用户则可以自由控制模型、推理后端、编码参数、批量任务和质量策略，同时能够查看性能与质量报告。

## 最终架构决议

RifeLove 正式确定采用：

C++20 + Qt 6/QML + FFmpeg + RIFE + ONNX Runtime CUDA + TensorRT + CUDA + SQLite + CMake。

产品以 Windows NVIDIA GPU 为明确目标，采用独立核心引擎、可替换模型、可插拔推理后端、精确时间轴、完整视频处理流水线和质量保护系统。

这份 Master Plan V1.0 作为 RifeLove 的完整产品范围基线。 后续实施可以分阶段进行，但不能把阶段性可运行版本误认为最终完成，也不应为了赶进度而取消核心质量、稳定性或兼容性要求。

下一步应当把这份总体计划拆解为正式的 Software Requirements Specification（SRS）、Architecture Design Document（ADD）和可执行开发任务清单，让每个模块都有明确接口、依赖、测试与验收标准，再进入实际编码。
