# Video restoration and enhancement

Status: the versioned contract, local pack verifier, offline Model Center catalog, and Studio/Queue integration for local spatial super-resolution are implemented. The FP32 SDR backend supports ONNX Runtime TensorRT EP with an explicit dynamic tile profile and automatic CUDA fallback; the selected session and fallback are recorded in reports. Native GTX 1660 SUPER x2 and x4 runs passed structural/timing validation. No restoration model has passed product quality, temporal/performance or weight-redistribution qualification.

RifeLove treats frame interpolation and video restoration as separate AI stages. RIFE predicts frames at new presentation times. Restoration models may denoise, deblur, reduce compression artifacts, or increase spatial resolution across one or more existing frames. A two-frame interpolation request is not an adequate contract for those jobs.

The initial C++ boundary is in `src/restoration/video_restoration_backend.hpp` and `.cpp`. Its versioned registry and validators cover model identity, task, stage placement, canonical SDR profile tags, ordered temporal context, scene/clip-edge context, preserved center PTS/duration/color metadata and spatial scale. Seven focused tests exercise this contract.

The local pack reader in `src/restoration/model_pack.hpp` and `.cpp` accepts a declarative `video-restoration` schema-v1 `model.json`. It verifies the ONNX file through streaming SHA-256, confines every referenced sidecar to the pack directory, and checks hash-bound license text, source manifest, validation report, adapter identity, declared tasks/placement/profile/window/scale and passed report cases. An adapter is selected from application-owned code; packs cannot include executable preprocessing. These checks establish local file consistency and matching declarations, not author authenticity or perceived quality. Four pack-verifier tests cover valid packs, changed data, capability mismatches, unsafe paths and invalid scale; a separate bounded streaming-hash test covers the graph file reader. The offline Model Center persists a separate restoration-pack catalog, shows declared tasks/window/scale, rejects unsupported families, and unregisters paths without deleting the local files.

`restoration::OnnxCudaVideoRestorationBackend` in `src/restoration/onnx_cuda_backend.hpp` uses shared ONNX Runtime session infrastructure with TensorRT EP and CUDA fallback. Its current adapter accepts one FP32 NCHW RGB image in `[0,1]`, with dynamic spatial dimensions and a declared integer scale; it tiles large images with overlap to cap temporary allocations. Direct CLI interpolation can opt in with `--restoration-model-dir`. The pipeline restores every output-rate frame after RIFE, retains the frame's PTS/duration/color contract, sets the declared output dimensions, and records restoration identity, actual provider and any setup fallback in reports. Studio and Queue expose local model selection for spatial super-resolution only: output-rate placement, zero temporal context, x2/x3/x4 scaling, a compatible declared SDR profile, and output dimensions no larger than 8192 pixels per side. They do not download or upload models. Job schema v4 persists the canonical local model directory and SHA-256 of `model.json`; execution rechecks the descriptor, and the serialized job configuration is part of checkpoint identity. No qualified restoration weight exists.

A local Real-ESRGAN x4plus evaluation pack was exported from the upstream checkpoint and validated numerically against the local PyTorch graph on two small tensor shapes. On the development GTX 1660 SUPER, a generated tagged 256x144, three-frame clip produced six 1024x576 frames at 60 FPS and passed output validation. The earlier CUDA run took 13.6 seconds overall, with 12.15 seconds in restoration. The TensorRT EP run spent 2.62 seconds in restoration; a cache-warm repeat completed in 9.0 seconds overall, including model setup. FFmpeg comparison of TensorRT output against CUDA output measured 40.83 dB PSNR/0.9933 SSIM over all six frames; the two generated frames averaged 36.20 dB/0.9800, while source-coincident frames were near-identical. This is backend-parity evidence, not visual-quality evidence against high-frame-rate ground truth. Cold initialization took about 100 seconds while TensorRT built engines and logged skipped tactics on the 6 GB GPU. The tiny synthetic clip does not qualify realistic performance, temporal stability or representative-resolution behavior. TensorRT may partition operators to CUDA, so the session name does not claim every model node ran on TensorRT. The checkpoint's redistribution terms are unresolved; its pack remains in ignored local evaluation storage and must not be bundled or uploaded.

A local Real-ESRGAN x2plus pack was exported using the upstream scale-2 pixel-unshuffle architecture and checked against its PyTorch graph on two tensor shapes. On the same GTX 1660 SUPER and tagged synthetic clip, the local CLI produced six 512x288 frames at 60 FPS. The warm run completed in 7.20 seconds including model setup, with 0.667 seconds attributed to restoration; the measured pipeline rate was 7.95 output frames per second. The first run took 45.26 seconds overall while initializing/building inference engines, while its measured media pipeline took 0.82 seconds. A fresh x4plus warm run produced six 1024x576 frames in 9.21 seconds including model setup, with 2.426 seconds attributed to restoration and a 2.28 output-frames-per-second pipeline rate. Both restoration sessions used the ONNX Runtime TensorRT execution provider without a reported setup fallback; the RIFE session also reported the TensorRT execution provider. These three-frame measurements establish local execution, output dimensions, frame count and timing behavior only. They do not establish subjective quality, temporal stability, or performance on real 1K/4K material. The x2plus checkpoint's redistribution terms are also unresolved, so both candidate packs remain in ignored local evaluation storage and must not be bundled or uploaded.

On 2026-10-26, a second tagged BT.709 SDR8 synthetic benchmark used six 960x540 frames at 30 FPS on the same GTX 1660 SUPER. TensorRT x2plus produced six 1920x1080 frames in 19.96 seconds end to end (0.301 output FPS; 12.25 seconds in restoration). TensorRT x4plus produced six 3840x2160 frames in 55.44 seconds (0.108 output FPS; 46.96 seconds in restoration). A combined RIFE 30-to-60 plus x2 restoration run produced 12 1920x1080 frames, including five RIFE-generated frames, in 32.63 seconds (0.368 end-to-end output FPS; 24.55 seconds in restoration). None of these runs reported a TensorRT-to-CUDA fallback. The 30 FPS scale-only runs had zero declared-duration error and at most 1/3000 second timestamp quantization; the combined run reported a 1/1000 second duration error from the Matroska clock. These synthetic results show that the current framewise ESRGAN path is far too slow for long clips on this GPU. They do not qualify visual quality, temporal stability, or expected speed on a different GPU. Do not make either ESRGAN model a default until a representative quality study and weight-license review pass.

## Product rules

- Processing remains offline by default. Source video, model selection, settings, temporary frames, reports, and task history stay on the user's computer.
- Restoration is optional and non-destructive. It writes to the selected output; it never replaces the source.
- A model cannot be called “best” from its name, paper result, or single synthetic benchmark. RifeLove must qualify each model for its task, content type, resolution, color profile, runtime and target GPU.
- Temporal stability is a release requirement. A model that improves single-frame sharpness while producing flicker, crawling texture, unstable text/HUD, or scene-cut contamination is not enabled as a video-restoration preset.
- A model pack contains declarative metadata and weights only. It cannot load or register executable code.
- No model weights are copied into Git. Downloads/imports are local, hash-checked, and accompanied by source, version, license scope and redistribution evidence.

## Proposed architecture

Continue the dedicated restoration interface rather than extending `IInterpolationBackend` or `IModelAdapter` with unrelated fields. The full product path still needs to represent:

- Restoration tasks: denoising, deblurring, compression cleanup and super-resolution.
- A temporal context window, including the center frame and exact rational presentation timestamps.
- The supported position relative to interpolation: source-rate frames before RIFE, or output-rate frames after RIFE. A model declares the positions it actually supports; the pipeline never guesses.
- Input and output color profiles, bit depth, spatial scale, dimension constraints, memory estimates and cancellation behavior.
- An owned output frame with its original presentation time preserved. Frame-count and audio timing stay under the existing timeline and muxing contracts.

The application service selects and validates the local model before starting a job. The scheduler applies bounded decode/inference/encode backpressure and never holds an unbounded video window in memory. Scene boundaries reset temporal context. Results retain model ID, adapter version, weight hash, backend, precision and settings in the local job identity and report.

## Qualification gate

Every candidate needs all of the following before a preset is offered:

1. Separate review of source-code and weight licenses, training-data restrictions where stated, attribution, and redistribution rights. A code license alone is not evidence that its weights can be bundled.
2. Verified source provenance and SHA-256 for every weight and sidecar.
3. Numerical comparison against paired ground truth where available, using task-appropriate metrics and exact PTS alignment.
4. Temporal review on real clips: camera motion, occlusion, scene cuts, grain, animation, fine text/HUD, compression damage, and low-light noise. Include frame-difference/flicker diagnostics and blind visual review.
5. Runtime and VRAM measurements on supported NVIDIA hardware, including the GTX 1660 SUPER development device, representative 1080p/4K input, cancellation, OOM handling, and software/backend failure behavior.
6. End-to-end tests proving duration, output cadence, source audio/subtitle policy, color tags, bit depth, and non-destructive publication.

No universal quality ranking is claimed. Fast/Balanced/Quality presets must be selected from measured task-specific evidence and remain clearly labeled by their tested content and hardware envelope.

## Candidate notes

- [RVRT](https://github.com/JingyunLiang/RVRT) is a temporal video-restoration research candidate for super-resolution, deblurring and denoising. Its official repository states that the project is released under CC-BY-NC. It is excluded from a redistributable default package unless the project obtains compatible rights.
- [VRT](https://github.com/JingyunLiang/VRT) is another temporal restoration research candidate. Its official repository also states CC-BY-NC terms, so it has the same distribution gate.
- [BasicVSR++](https://github.com/ckkelvinchan/BasicVSR_PlusPlus) is a temporal video super-resolution/restoration candidate, and its official source repository is Apache-2.0. Pretrained weights are linked as separate downloads without an explicit weight-redistribution statement in the repository README; therefore the weights stay out of RifeLove packages until their rights and training-data terms are resolved.
- [Real-ESRGAN](https://github.com/xinntao/Real-ESRGAN) labels the repository BSD-3-Clause and its model zoo links x4plus weights as a release asset ([license](https://github.com/xinntao/Real-ESRGAN/blob/master/LICENSE), [model zoo](https://github.com/xinntao/Real-ESRGAN/blob/master/docs/model_zoo.md), [release](https://github.com/xinntao/Real-ESRGAN/releases/tag/v0.1.0)). RifeLove has not established whether that repository license clearly covers redistribution of the checkpoint asset. Its restoration network is image-oriented, so framewise use also needs temporal, color and end-to-end qualification.
- The Real-ESRGAN x4plus local experiment above uses a framewise image model and is particularly expensive on the development GPU. Keep this candidate out of distributable packages and OSS releases until RifeLove has documented weight rights and completed quality/performance qualification. Upstream issues [1015](https://github.com/xinntao/Real-ESRGAN/issues/1015) and [1016](https://github.com/xinntao/Real-ESRGAN/issues/1016) discuss the separate `realesr-general-x4v3` checkpoint; they do not resolve the x4plus license scope.
- [Real-ESRGAN AnimeVideo-v3](https://github.com/xinntao/Real-ESRGAN/blob/master/docs/anime_video_model.md) is a small, anime-specific model with X1–X4 scale options. The upstream video workflow extracts frames, applies the image network, and merges them back; it provides no temporal context. Treat it as an anime-only spatial candidate, not as general or temporally stable video restoration. The upstream code is BSD-3-Clause, but its README does not state a separate license for the released checkpoint, so redistribution remains unresolved.
- [SwinIR](https://github.com/JingyunLiang/SwinIR) has published x2 and x4 classical-SR weights and an x4 real-world model. The official code is Apache-2.0, but the checkpoint release does not attach an explicit weight license. It is an image-restoration network without temporal context; its official benchmark reports 0.539 seconds for one 256x256 LR image on an RTX 2080 Ti, so it is not a plausible GTX 1660 SUPER video default without a much smaller measured workload. Keep it as a local research candidate only until weight terms and video flicker/performance are cleared.
- [HAT](https://github.com/XPixelGroup/HAT) publishes x2 training configurations and x4 image super-resolution models, including real-world GAN variants. The repository code is Apache-2.0 and provides tiled inference for limited GPU memory, but it does not state a separate license for its downloaded checkpoint assets. Its paper benchmarks are single-image SR, not video-temporal quality; the full HAT model is also substantially larger than SwinIR in the upstream x4 comparison (20.8M vs. 11.9M parameters). Keep it out of default presets and distributed packages until checkpoint rights and local-video qualification are resolved.
- Current shortlist: continue testing Real-ESRGAN x4plus only as a general SDR baseline, add the smaller AnimeVideo-v3 only for animation, and evaluate a native general x2 model before enabling x2. No candidate is yet qualified as a shipping default. Do not infer video quality from image-only PSNR leaderboards or convert an ambiguous model checkpoint into a distributable pack.
- [PS-SR](https://github.com/HiDream-ai/PS-SR), a CVPR 2026 video super-resolution research system, has Apache-2.0 code but its published setup requires Linux, Python 3.10, PyTorch 2.7.1, DiffSynth-Studio, Wan2.1-T2V-1.3B and separately downloaded DAPE, RAM and PS-SR checkpoints. It is not a ready Windows/ONNX package for the current target; every dependent model's license, GPU-memory needs, exportability and local quality would need separate qualification.

These are research notes, not a selected model or an endorsement that any candidate is universally superior. A future permissively licensed or project-trained temporal model can replace them after it passes the same gates.
